# TeamH4C: what its public work actually shows

Reviewed 2026-10-26 from [TeamH4C's official site](https://h4c.team/) and member-authored posts. TeamH4C describes itself as a South Korean white-hat team with CTF, AI security, academic, defensive, and research divisions. Its [history page](https://h4c.team/history) lists contest results and vulnerability disclosures. Those are team-published records; they do not reveal every member's private tool stack or prove that a tutorial's setup is team-wide practice.

| Original TeamH4C source | Publicly demonstrated or discussed | Useful adoption here |
| --- | --- | --- |
| [Local LLM vulnerability analyzer](https://h4c.team/en/posts/6) | One author built a tool-calling binary-analysis prototype using Ollama, Qwen2.5 3B, Ghidra Headless, and `pyghidra-mcp` over stdio, with prompts meant to filter weak candidates. The post also compares one-shot, tool-calling, and retrieval-based analysis. | Ghidra is already installed; keep this free prototype as a reference for supplied binaries. Do not install an old version or give a new MCP server broad file access merely because it appears in a tutorial. Test on an owned sample and judge the actual decompilation and evidence. |
| [Multi-agent system design](https://h4c.team/en/posts/7) | A member describes role specialization, an orchestrator, explicit output formats, and verification; they report a separate 11-agent smart-contract-audit experiment and its limits. Their OpenCode/Claude configurations are examples, not a confirmed TeamH4C-wide stack. | `default` orchestrates BUGGY, SCOUT, and PROOF with narrow tasks and evidence handoff. Add a role only for a distinct question; the parent checks results against artifacts. |
| [What is an agent?](https://h4c.team/en/posts/42) | The article argues that a tool loop needs explicit decision criteria: when to gather more evidence, revise a plan, stop, or escalate. | Preserve stop conditions, budgets, and falsifiers in the lead card; don't call repeated tool use “autonomy” without better decisions. |
| [README prompt-injection lab](https://h4c.team/en/posts/9) | A toy Ollama/Python wrapper demonstrates how untrusted README instructions can induce an agent's file-read tool to access `.env`; the wrapper's trust decision is the decisive boundary. | For AI/MCP research, test the tool permission and lower-trust input boundary in an owned lab, logging the action rather than scoring only the model's answer. |
| [Web CTF agent analysis](https://h4c.team/en/posts/74) | A review of agent solve failures distinguishes vulnerability discovery, objective completion, and final acceptance. | Keep verification criteria in the working evidence ledger. In publish-ready prose, show the observed decisive check without a boilerplate paragraph about tests that were not run. CTF writeups remain a later HACKSPACE phase. |
| [Public GitHub organization](https://github.com/h4c) | Public repositories, including its site. | A source for public materials, not evidence of the private research environment. |

The strongest transferable pattern is **specialize → act through controlled tools → independently verify → preserve the exact evidence**. This is consistent with the [Wiz/XBOW/Hacktron workflow comparison](WIZ-XBOW-HACKTRON.md) and [Gray Swan agent-boundary research](GRAY-SWAN.md), while the direct tool names above come from TeamH4C's own public examples. The repo does not claim TeamH4C uses Hermes, Caido, or this workbench.
