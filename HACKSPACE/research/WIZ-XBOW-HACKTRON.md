# What to borrow from Wiz Code, XBOW, and Hacktron

Reviewed 2026-10-26 against the vendors' **public** documentation and disclosures. This compares workflows, not independently measured detection quality. All three are commercial offerings; this local workbench uses their published ideas without implying access to their private products or backend data.

| Stage | Publicly described approach | Improvement for Hermes/Codex |
| --- | --- | --- |
| Choose work | [Wiz Code](https://www.wiz.io/blog/agentic-code-security) describes layered deterministic checks, continuous AI analysis, and targeted deep testing selected using code-to-cloud exposure. | Start with current scope and a known asset/code path; weigh reachability, trust boundary, potential impact, duplicate risk, and decisive-test cost before broad exploration. |
| Understand the system | [Wiz Code](https://www.wiz.io/platform/wiz-code) links code, cloud, identity, runtime, and attack surface. [Hacktron's white-box method](https://www.hacktron.ai/pentests) starts from source and user flows. | Give BUGGY relevant supplied code, architecture, roles, Caido history, deployment context, and current policy; never infer deployed reachability from code alone. |
| Coordinate specialists | [Wiz](https://www.wiz.io/blog/introducing-wiz-agents) describes Red (discovery), Blue (investigation), and Green (resolution) agents. [Hacktron's Gumroad account](https://www.hacktron.ai/blog/introducing-hacktron) describes specialized LLM, AST, and vulnerability-class agents with human review. | Route exploratory lead work to BUGGY, independent falsification to PROOF, and primary-source/payout/prior-art work to SCOUT. Keep each result short and evidence-linked. |
| Control active assessment | [XBOW's assessment setup](https://docs.xbow.com/console/how-to/run-assessment/) separates **Attackable**, **Allow Visit**, and **Blocked** domains, protects special URLs, checks authentication, and sets target-protection and impact limits before running. | Record those distinctions in a private engagement card. For bug bounty programs, use the program's *own* automation and rate rules; XBOW's enterprise rate examples are not transferable permission. |
| Verify candidates | [XBOW's classification](https://docs.xbow.com/console/reference/vulnerability-classification/) distinguishes deterministic validators from agent-confirmed classes. [Wiz Atlas](https://www.wiz.io/blog/atlas-ai-vulnerability-researcher) says it validates its reported code findings with working exploits. [Hacktron's sample Gumroad report](https://www.hacktron.ai/reports/Gumroad_01.pdf) records human triage of 12 candidates into eight vulnerabilities and four weaker issues. | For each candidate, preserve a baseline, one changed condition, a negative control, and direct server/tool/state evidence. PROOF should challenge the root cause and alternative explanations. A model-generated PoC is a hypothesis until reproduced. |
| Demonstrate impact | [XBOW impact demonstration](https://docs.xbow.com/console/reference/impact-demonstration/) separates confirmed exploitability from optional escalation depth. | Stop at minimum proof on live in-scope systems. Do not pivot across accounts or systems unless the written program permits it. Keep speculative downstream effects separate from observed impact. |
| Preserve trace and gaps | [XBOW result guidance](https://docs.xbow.com/console/how-to/explore-and-fix-results/) exposes reproducible findings and full test traces; its [coverage map](https://docs.xbow.com/console/guidance/interpreting-results/) records untested endpoints/classes. | Keep redacted Caido request IDs, role labels, terminal outputs, actual screenshots, and a short diary. Mark untested boundaries as gaps, not clean results. |
| Fix and learn | [Wiz's Green Agent](https://www.wiz.io/blog/introducing-wiz-agents) connects a finding to root cause and owner; [Hacktron's Gumroad account](https://www.hacktron.ai/blog/introducing-hacktron) describes proposed code fixes and merged PRs. | For owned code, trace the source, suggest a focused fix, and verify it with a regression check. For bounty targets, report the supported bug and let the program own remediation. |

## Additional high-value lessons

- [XBOW's Chrome case](https://xbow.com/blog/xbow-built-a-chrome-full-chain-exploit) says the first chain included a bug Google already knew about; modular independent primitives let its team replace that piece. The [Chromium issue](https://issues.chromium.org/issues/547965190) records the later chain and $250,000 VRP reward. A chain needs evidence for **each** boundary and an explicit prior-art check; a payout is not a general expectation.
- [Wiz's Snowflake workflow disclosure](https://www.wiz.io/blog/red-agent-snowflake-copilot-cicd-bug) shows how a short-lived CI script-injection window was found and fixed. Read the current corrected attribution: a PR's AI co-author label alone does not prove which lines AI generated. This is a useful warning against attractive but unsupported causal stories.
- [Hacktron's Fider comparison](https://www.hacktron.ai/blog/hacktron-vs-xbow-and-aikido) is Hacktron's own test and grading, not an independent product ranking. Hacktron itself reports that many automated severity labels were too high. Treat vendor benchmarks as leads for evaluating a method, never as proof that a particular finding is critical.
- [Hacktron's OpenAI case](https://www.hacktron.ai/blog/hacking-openai) reports a $6,500 reward for an OpenAI-side issue and reproduces an OpenAI clarification that a related Discourse-hosted site was excluded from OpenAI's bounty scope. Preserve that distinction; an AI-assisted result does not enlarge a program's scope.

## Local loop to use

1. **SCOUT:** current program terms, original prior art, technology/version, payout eligibility, and a dated research card.
2. **BUGGY:** one promising trust-boundary hypothesis, source/data-flow trace or passive Caido evidence, minimal authorized comparison, and a stop condition.
3. **PROOF:** independent baseline/control check, reproducibility, competing explanation, exact observed impact, and duplicate-root analysis.
4. **Main agent:** choose supported verdict, preserve private evidence, draft with `ywh-reporting` when requested, and record coverage gaps and next steps.

Parallel agents save time only when their questions are independent. They do not multiply permission to contact a target; all inherit the same written scope and rate budget. The workflows above apply to broad bug bounty research, with extra attention to AI agent, cloud, and code-to-cloud boundaries.
